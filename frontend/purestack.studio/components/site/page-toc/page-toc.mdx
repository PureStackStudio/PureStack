The TOC beside this guide is the component in use. Its links come from the final rendered article, including headings produced by Regor. The playground below adds browser content to that same outline. On smaller screens, open **on this page** to see the links.

## Start with headings

Use the default doc template and write your sections. PureStack supplies the PageToc; you do not need to add a second component.

```mdx
---
template: doc
layout:
  showToc: true
---

# Getting started

## Install

### Choose a package manager

## Configure
```

The TOC starts at **Install**, nests **Choose a package manager** beneath it, and continues with **Configure**. The page's single h1 is treated as its document title and omitted from the list.

| Setting | Default doc layout |
| --- | --- |
| `layout.showToc: true` | Show the panel when the rendered article has TOC entries. A lone h1 is not enough. |
| `layout.showToc: false` | Omit the default panel and its TOC runtime. |
| `layout.showToc: always` | Retain the panel and runtime even without entries, ready for client content. |
| No page override | Use `pageToc.enabled` from site config. |

Both `true` and `always` override a disabled site default. SSG collects the article from the existing rendered DOM; it does not render your content a second time to discover headings.

## Try client updates

Each section uses the text currently in the textbox, then the textbox advances to **Client section 2**, **Client section 3**, and so on. An existing trailing number is incremented in place. Change the heading text and choose **Rename last**: the label changes while its existing ID stays stable. Move, exclude and remove sections to see the outline follow the DOM.

Turn off **Refresh after every change** to separate the two steps. The page changes immediately; its TOC keeps the previous links until you choose **Refresh TOC**. Clearing these sections leaves the guide's other entries intact.

The playground is a Regor app mounted with `RegorApp`. Its exported class context owns the state and actions. Focused controls and section components compose PureStack's `FormInputField`, `FormCheck`, `Btn`, `Flex` and `Panel`. Controls access the ancestor context with `requireContext`; a keyed `r-for` preserves section elements and their IDs. `onMounted` performs the initial scan, and later actions refresh directly after a `batch` has flushed its DOM bindings.

## Refresh from a client app

Use `onMounted` for the initial scan, when the component's headings are in the DOM. Regor applies ref updates synchronously, so later actions can update state and call `refresh()` immediately afterwards. When grouping changes with `batch()`, refresh after that call returns. A mounted hook runs once; it does not run again for title changes, reordering or removals.

Mount the app inside the page's content:

```html
<RegorApp id="app-content" class="d-block" src="./app.ts"/>
```

```ts
import type {} from '@purestack/ts-page-scripts'
import { defineButtonComponents } from '@purestack/ts-components'
import { createApp, defineComponent, html, onMounted, type SRef, sref } from 'regor'

interface Section {
  key: number
  title: string
}

export interface SectionList {
  sections: SRef<Section[]>
  addSection: () => void
}

const sectionList = defineComponent<SectionList>(html`<div>
  <Btn tone="accent" @click="addSection">Add section</Btn>
  <section r-for="section in sections" :key="section.key">
    <h2>{{ section.title }}</h2>
  </section>
</div>`, {
  context: () => {
    const sections = sref<Section[]>([])
    let nextKey = 0
    const refresh = () => window.tsSsgPageToc?.refresh()

    onMounted(refresh)

    return {
      sections,
      addSection: () => {
        const key = ++nextKey
        sections([...sections(), { key, title: `Account settings ${key}` }])
        refresh()
      },
    }
  },
})

createApp({ components: { SectionList: sectionList, ...defineButtonComponents() } }, {
  selector: '#app-content',
  template: html`<SectionList/>`,
})
```

The refresh reads the current article, assigns IDs to new headings, rebuilds the links in DOM order, and updates active-section tracking. It preserves panel preferences and the IDs already on your headings.

Call it after adding, removing, renaming or reordering sections, or changing `data-toc-ignore`. Refresh once after a group of changes. To remove an app's entries on unmount, remove its content and refresh again.

For fetched content, await your loader in a component action or mounted hook, assign the resolved entries to the sections ref, then refresh. Keep loading and error state in your app. The same `refresh()` API works with any app that renders headings into the content container.

## Heading and ID rules

| Rule | Result |
| --- | --- |
| h1, h2 and h3 inside the content container | Collected in DOM order and nested by heading level. |
| One h1 at the root of the outline | Its children become the visible TOC entries. Multiple h1 roots remain visible. |
| h4 through h6, or a heading with no text | No entry. |
| `r-if="false"` | No rendered heading, so no entry. |
| `r-show`, CSS visibility or a closed disclosure | The heading still exists in the DOM; hiding it visually does not exclude it. |
| A heading or ancestor with `data-toc-ignore` | No entry, even when the heading is visible. |
| Heading with an existing ID | Keep it, including after renaming or reordering. |
| Heading without an ID | Derive an ID from the rendered title, adding a suffix to avoid existing page IDs. |

Generated IDs use lowercase ASCII letters and digits, with punctuation and spaces becoming hyphens. Duplicate **Installation** headings receive IDs such as `installation` and `installation-2`. A title without ASCII letters or digits uses `section` and numbered suffixes. For translated titles, public deep links or headings that change often, author an explicit ID:

```html
<h2 id="account-settings">Account settings</h2>
```

A generated ID is assigned once to that DOM element. Refreshing after a rename keeps it. Replacing the element with a new heading without an ID generates an ID for the new element. Authors are responsible for keeping explicitly supplied IDs unique.

Exclude an individual heading or a whole example:

```html
<h3 data-toc-ignore>Preview label</h3>

<div data-toc-ignore>
  <h2>A heading inside an embedded interface</h2>
</div>
```

## Choose the content container

The standard doc layout already marks its article. Custom templates can use `data-page-content` to identify the area whose headings should become entries:

```html
<main>
  <article data-page-content>
    <!-- Static content and client app mounts go here. -->
  </article>
</main>
```

Discovery uses the first matching `data-page-content` container, then the standard `.doc-main .doc-content` article, then the first `main`, then the body. Headers, navigation and footers outside the selected container do not participate. The same discovery rules apply during SSG and browser refresh.

## Supply an explicit outline

Custom templates and standalone examples can pass `outline` instead of using the page's discovered headings. Every ID must identify a real target in that document. The built-in doc template already adds its own PageToc.

```html
<PageToc
  title="In this example"
  :outline="[
    { id: 'overview', title: 'Overview', depth: 2, children: [
      { id: 'requirements', title: 'Requirements', depth: 3 }
    ] },
    { id: 'next-steps', title: 'Next steps', depth: 2 }
  ]"
/>
```

SSG and a browser `refresh()` both preserve an explicitly supplied outline. Only `refresh(root)` with this TOC as `root` rebuilds it from the content container, replacing its current entries. For scroll tracking, use h1–h3 elements as targets.

## Browser API

The standard runtime exposes `window.tsSsgPageToc`. Its TypeScript declaration is exported with `@purestack/ts-page-scripts`.

| Method | Purpose |
| --- | --- |
| `refresh(root?: Element \| null): void` | Read the current content and rebuild links and section tracking. This is the app-facing API. |
| `hydrate(root?: Element \| null): void` | Bind behavior to an existing TOC. Component output calls this automatically; it does not rediscover headings. |

Without `root`, `refresh` rebuilds every TOC without an explicit `outline`, and `hydrate` selects the first `.page-toc`. To target one instance, pass its nav element or a container around it. **The argument selects the TOC, not the heading container**; `data-page-content` selects the content.

```ts
const panel = document.querySelector('#custom-toc')
if (panel) window.tsSsgPageToc?.refresh(panel)
```

## Troubleshooting

| Symptom | Check |
| --- | --- |
| A client-only page has no TOC | Set `layout.showToc: always` before building. `refresh()` updates an existing panel; it does not create a missing layout. |
| The TOC shows old links | Refresh after the DOM update, including after unmounting an app. |
| A heading does not appear | Check its level, text, content container, `data-toc-ignore` ancestors and conditional rendering. |
| A hidden example appears in the TOC | CSS visibility does not remove headings from the DOM. Add `data-toc-ignore`. |
| A link reaches the wrong element | Check for duplicate authored IDs. Generated IDs avoid collisions with IDs already on the page. |
| A renamed heading keeps its old fragment | Existing IDs are preserved intentionally. Keep that ID for stable links, or choose a new explicit ID. |
| A second TOC updates | Pass the intended panel to `refresh(root)`. The default target is the first `.page-toc`. |
