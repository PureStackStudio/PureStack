# Plugins

A plugin is a named object that extends how PureStack builds your site. Each of its fields adds one kind of extension, so a single plugin can bring a brand skin together with the components and page layout that go with it. Find the field for what you need:

| To | Use |
| --- | --- |
| Give the site its own colors | [`skins`](#add-a-skin) |
| Reuse a piece of markup in your pages | [`components`](#add-components) |
| Lay out some pages differently | [`templates`](#add-page-templates) |
| Change how Markdown turns into HTML | [`markdown`](#transform-markdown) |
| Build pages from data, such as one page per tag | [`pages`](#generate-pages) |
| Change a whole page, header and footer included | [`hooks.onPageDocument`](#change-a-pages-dom) |
| Write extra files, such as a JSON page index | [`hooks`](#write-extra-files) |
| Add styles or run code at other points in the build | [`hooks`](#run-code-during-the-build) |
| Answer requests while you develop | [`devMiddleware`](#handle-requests-in-development) |

## Add your first plugin

To use an installed plugin without writing TypeScript, list its package in
`siteConfig.json`. For example, install `@purestack/ts-images`, then enable image
optimization:

```json
{
  "plugins": ["@purestack/ts-images#imagesPlugin"],
  "extensions": {
    "images": { "widths": [480, 960, 1440] }
  }
}
```

Use `package#exportName` to select a named export, for example
`"@purestack/ts-images#imagesPlugin"`. Without a suffix, PureStack selects the
default export. Each selected export must be a plugin object or a no-argument
factory. Packages can expose multiple plugins; list each export separately:

```json
{
  "plugins": [
    "@purestack/ts-page-scripts#consentPlugin",
    "@purestack/ts-page-scripts#analyticsPlugin"
  ]
}
```

The suffix is the JavaScript export name, not the plugin's `name`. Package
subpaths also work: `package/subpath#exportName`. PureStack loads selections for
builds, publishing, and development, and reloads them when this JSON file changes.
Each plugin owns its settings; listing `imagesPlugin` enables
its defaults even without `extensions.images`. Set `extensions.images.enabled`
to `false` to disable optimization. An explicit plugin instance in
`purestack.config.ts` replaces a JSON-selected plugin with the same name.

Both config formats use PureStack's own copy of a package when available so
shared registries stay together; other packages resolve from the site.
Plugin declarations execute installed JavaScript with the build process's
permissions, so treat changes to `plugins` as code changes even when a CMS edits
other site settings.

For local plugins and custom callbacks, use the TypeScript setup below.

Keep plugins in a folder of their own, beside the content folder:

```text
content/
  siteConfig.json
  purestack.config.ts
  index.mdx
plugins/
  site.ts
package.json
```

This plugin adds a component that shows a release badge:

```ts
// plugins/site.ts
import { definePlugin } from 'purestack'
import { defineComponent, html } from 'regor'

export interface ReleaseBadge {
  version?: string
}

export const sitePlugin = definePlugin({
  name: 'site',
  components: () => ({
    releaseBadge: defineComponent<ReleaseBadge>(
      html`<Badge tone="success" variant="surface">v{{ version }}</Badge>`,
      { props: ['version'] },
    ),
  }),
})
```

List it in `purestack.config.ts`, next to `siteConfig.json`:

```ts
// content/purestack.config.ts
import { defineConfig } from 'purestack'
import { sitePlugin } from '../plugins/site'

export default defineConfig({
  plugins: [sitePlugin],
})
```

Use the component in a page:

```mdx
Version 2.0 is out. <ReleaseBadge version="2.0" />
```

Start the development server as usual:

```sh
yarn purestack serve --content ./content
```

The badge appears on the page. Change its `tone` in `plugins/site.ts` while the server runs: the site rebuilds and the page reloads. `build` and `publish` load the same config, so the published site gets the same badge.

## Standard plugins

PureStack includes nine plugins automatically in `build`, `serve`, and `publish`:

| Package | Factory | Provides |
| --- | --- | --- |
| `@purestack/ts-components` | `componentsPlugin()` | Standard components, icons, and component styles |
| `@purestack/ts-theme` | `themePlugin()` | The `doc` and `splash` templates, generated theme CSS, favicons, theme switching, and Markdown table presentation |
| `@purestack/ts-page-scripts` | `pageScriptsPlugin()` | Menus, navigation, code copying, search, TOC, Tabs, and Modal runtimes |
| `@purestack/ts-page-scripts` | `authStateHintPlugin()` | Early signed-in state hint |
| `@purestack/ts-page-scripts` | `consentPlugin()` | Consent browser runtime |
| `@purestack/ts-page-scripts` | `analyticsPlugin()` | Direct or consent-managed GA4 integration |
| `@purestack/ts-seo` | `seoPlugin()` | Social previews, canonical URLs, and translated alternate links |
| `@purestack/ts-highlight` | `highlightPlugin()` | Shiki or highlight.js code highlighting |
| `@purestack/ts-pagefind` | `pagefindPlugin()` | Full-build and lazy development search indexing |

The stylesheet provider initializes before component factories, then all config hooks run in plugin order. Names do not affect initialization. Components belong to each build, so hooks can override them through `context.components`. The theme and page runtime plugins supply head templates that run before the selected page template, preserving its ability to inspect or change the completed head. The lifecycle hook set is unchanged.

Metadata defaults compose through `headConfig({ site, pageInfo })` in plugin order, before explicit frontmatter `head` overrides and before head markup is rendered. It returns `BasicHeadConfig` or a promise. The SEO plugin uses this contribution for Open Graph, Twitter, canonical URLs, and translated alternate links; page templates receive the completed `headConfig`. Basic titles, descriptions, explicit head settings, and `index: false` enforcement remain in core.

Auth hints, consent, and analytics are independent plugins in `ts-page-scripts`. The analytics plugin contributes automatic GA4 consent services during configuration resolution, before any factory or lifecycle hook runs. Omitting it removes automatic registration and direct tracking scripts. Explicitly configured consent services remain available. Analytics never bypasses enabled consent when the consent runtime plugin is omitted.

To choose the standard integrations yourself, disable the automatic set and list the plugins you want in `siteConfig.json`:

```json
{
  "defaultPlugins": false,
  "plugins": [
    "@purestack/ts-theme#themePlugin",
    "@purestack/ts-components#componentsPlugin"
  ]
}
```

Omitting `defaultPlugins` keeps the automatic set enabled. An explicit
TypeScript/programmatic `defaultPlugins` value overrides the JSON flag.
Development reloads changes to either setting.

The same selection is available in `purestack.config.ts`. The factories are exported from `purestack`, `@purestack/ts-ssg`, and their individual packages:

```ts
import { componentsPlugin, defineConfig, themePlugin } from 'purestack'

export default defineConfig({
  defaultPlugins: false,
  plugins: [themePlugin(), componentsPlugin()],
})
```

This keeps the layouts and components while omitting automatic social metadata, page runtimes, code highlighting, and search indexing. Theme switching, favicon generation, and Markdown table wrappers belong to the theme plugin. Tabs and Modal scripts belong to the page scripts plugin, including automatic component embeds and explicit frontmatter settings. Without the theme plugin, another plugin must supply your page templates and any CSS output you need.

An explicitly listed standard plugin replaces the automatic instance by name and keeps its initialization position. You can also use `createDefaultPlugins()` to obtain the complete set. In programmatic builds, use `options.defaultPlugins` alongside `options.plugins`.

The highlighting plugin selects the configured backend. Configure native backend factories through `highlightPlugin({ createShiki, createHighlightJs })`, or supply `markdown.createHighlighter({ mdx, cache })` for a different engine. The generic provider returns `{ codeToHtml(code, lang?) }`. Ordinary providers override the default without constructing it; per-language `markdown.resolveHighlighter` callbacks retain precedence.

The Pagefind plugin supplies a `search` provider. To use another engine, replace `purestack:pagefind` or disable the default set and install your own provider. The builder supplies excluded output paths and the rendered-page list for lazy requests, and manages invalidation on edits and deletions. Sitemap and robots generation remain built in.

## Configure a plugin

`resolveSiteConfig(input)` returns `DefaultSiteConfig` for the untouched standard set. Calls supplying a `plugins` array return `SiteConfig`, even when automatic defaults remain enabled, because a supplied plugin can replace a standard owner by name.

Plugins contribute configuration through optional, synchronous `config.resolve`, `config.normalize`, and `config.finalize` functions, each receiving `{ config, input, file }` and returning an object to merge into config. Do not mutate the inputs. All resolvers run first in plugin order to supply defaults and overrides. All normalizers then validate and canonicalize the completed overrides. Finally, all finalizers derive dependent settings from the normalized config. Finalizers should not change the inputs used by other finalizers. Every phase finishes before highlighters, Markdown processors, styles, search providers, components, and templates initialize. Analytics derives its automatic GA4 consent service only after every normalizer finishes, regardless of plugin order. The existing `onConfigResolved` hook still runs after factories. Publishing applies its output-directory and minification overrides after configuration composition.

Custom site settings belong under `extensions` in `siteConfig.json`. File values merge with programmatic input, which takes precedence. The standard JSON schema allows plugin namespaces here while continuing to reject unknown top-level fields. Each plugin owns validation, defaults, and normalization for its namespace. Other namespaces are preserved.

`resolve` and `normalize` receive `SiteConfigDraft`: core fields are ready, while plugin settings can still be partial, including nested extension values. `finalize` receives normalized `SiteConfig` after all selected owners finish normalization. Factories run afterwards. Importing a plugin's setting types does not install its owner; select that plugin before depending on its normalized settings.

```json
{ "extensions": { "brand": { "label": "Acme" } } }
```

Use TypeScript module augmentation for typed settings:

```ts
import { definePlugin } from 'purestack'

declare module '@purestack/ts-common' {
  interface SiteExtensions {
    brand?: { label: string }
  }
}

export const brandPlugin = definePlugin({
  name: 'brand',
  config: {
    resolve({ config }) {
      const brand = config.extensions.brand
      if (brand !== undefined &&
          (brand === null || typeof brand !== 'object' ||
           typeof brand.label !== 'string')) {
        throw new Error('extensions.brand requires a string label.')
      }
      return { extensions: { brand: { label: brand?.label ?? 'Docs' } } }
    },
  },
  components(config) {
    // config.extensions.brand contains the normalized settings here.
    return {}
  },
})
```

`resolveSiteConfig(input, { plugins, defaultPlugins })` composes the supplied plugin instances with the standard plugins by default. This synchronous helper does not apply JSON plugin selection (`plugins` or `defaultPlugins`) or load `purestack.config.ts`. Plugin-owned sections (`style`, `docLayout`, `pageToc`, `logo`, `auth`, `consent`, `analytics`, `pagefind`, and `preview`) are optional in `SiteConfig`: an omitted plugin does not supply defaults or validate its unused input. A replacement plugin reads its settings from `input` and `file`, then contributes normalized config. Analytics also resolves explicitly configured consent when its browser runtime is omitted, so enabled consent is never bypassed. Configuration contributions are synchronous and may run whenever a project configuration is resolved; keep file writes and other side effects in lifecycle hooks.

`config.cache` is `false` when a run uses `--no-cache` or `options.cache: false`. A plugin that keeps a persistent cache outside the output directory should neither read nor write it then. Site settings cannot change this flag, and it never invalidates incremental output.

Builder style state is isolated across asynchronous operations, including concurrent sites. Its owned theme options remain linked to `context.config.style.theme`, so in-place config-hook changes and `themes.setOptions` update page colors, CSS, and generated favicons consistently. Head, metadata, template, Markdown, provider, and lifecycle errors identify their owning plugin and preserve the original cause. Markdown wrappers preserve unified presets, duplicate-plugin option merging, and callback transforms.

## Optimize images

Image optimization is optional. Install `@purestack/ts-images` alongside PureStack and add it to your existing plugin list:

```ts
import { defineConfig } from 'purestack'
import { imagesPlugin } from '@purestack/ts-images'

export default defineConfig({
  plugins: [imagesPlugin({ widths: [480, 960, 1440] })],
})
```

Ordinary Markdown images and rendered HTML images receive responsive AVIF/WebP sources, JPEG/PNG fallbacks, dimensions, and loading defaults. Originals remain available for links and downloads. Remote images, SVGs, animations, existing `picture` markup, and images with `srcset` pass through. Use `data-image-preset="hero"` for eager priority images, `data-image-preset="screenshot"` for lossless output, or `data-image-optimize="false"` to keep an individual image unchanged. Set `sizes` for your actual image layout.

The plugin owns its `extensions.images` settings, persistent cache, and encoder limits. It uses the generic asset contribution: `assets(config)` returns a per-site processor with a unique namespace and `processPage(input)`. This runs after all `onPageDocument` hooks, before URL rewriting. `resolveSource(element, url)` resolves local inputs and registers dependencies; `dependOn(relPath)` registers additional inputs; `emit(fileName, bytes)` atomically writes an owned file and returns its URL. Use content-addressed names and await all writes. Core handles base paths, incremental invalidation, shared references, manifest persistence, and cleanup when pages or processors disappear. The builder contains no image format or encoder selection.

Asset processors run in order within each page, and different page requests can run them concurrently. Keep page-local state inside `processPage`; coordinate shared caches and queues within the processor instance. Await source resolution and emission before returning. Input methods then close, and detached work cannot emit files after page completion. Later processors see earlier DOM edits, while `resolveSource` continues to resolve original content files only. Combine transforms inside one processor when they need intermediate generated bytes. Ownership receipts and processor instances remain private to the builder.

## How the config loads

- **Where it lives.** The CLI looks for `purestack.config.ts` in the folder passed to `--content`. It must default-export `defineConfig({ plugins: [...] })`.
- **Your own files.** The config and the files it imports are bundled when the config loads, so they can be TypeScript and live in any folder, with no build step.
- **Packages.** Packages load from `node_modules` as they are. `purestack`, `regor`, and the `@purestack/*` packages always resolve to the copies the CLI runs, so your components and skins register where the build looks for them. Install the ones you import anyway, so your editor knows their types.
- **Reloading.** `serve` loads the config again, and rebuilds the site, when the config or one of your files changes. A package loads once; restart `serve` after updating one.
- **Mistakes.** When a reload fails, the terminal shows the error and the site keeps its last working plugins until you fix it.

Keep plugin code outside the content folder to make its build-time role clear. TypeScript files inside content are not automatically published; entries referenced by [PageScript](/components/runtime/page-script/) are bundled for the browser. `purestack.config.ts` is a build-time configuration file even though it lives inside content.

## Add a skin

A skin is a light and dark palette pair. This one starts from the standard skin with brand colors:

```ts
import { themeSkins } from '@purestack/ts-style'
import { definePlugin } from 'purestack'

export const sitePlugin = definePlugin({
  name: 'site',
  skins: {
    brand: {
      create: () =>
        themeSkins.standard.create({
          accent: '#4b64c8',
          neutral: '#293047',
        }),
    },
  },
})
```

Select it in `siteConfig.json`:

```json
{
  "style": { "theme": { "skin": "brand" } }
}
```

Give a skin its own name; `standard` belongs to the built-in skin. The [Themes guide](../styling/themes) covers palettes in depth.

## Add components

`components` returns your [Regor](./regor) components by name, as the first plugin above does. It receives the resolved site config, so a component can depend on settings such as `config.siteTitle`.

- **Create them inside `components`.** Regor needs the page document that the build sets up before it calls `components`. A component defined at the top of a module fails with `document is not defined`. To keep components in their own files, export a function that creates them, and call it from `components`.
- **Names.** Register a component in camelCase, like `releaseBadge`, and write it in PascalCase in your pages: `<ReleaseBadge>`.
- **Built-in components.** A component's template can use any [built-in component](/components/), as `<Badge>` does in the release badge. A component with a built-in one's name replaces it.
- **Browser behavior.** Components render to HTML when the site builds. For behavior in the browser, add a [page script](/components/runtime/page-script/).

## Add page templates

A template renders a whole page around its content. Build the markup with `h` from `@purestack/ts-html`:

```ts
import { h } from '@purestack/ts-html'
import { definePlugin } from 'purestack'

export const sitePlugin = definePlugin({
  name: 'site',
  templates: {
    landing: ({ head, bodyHtml, headerHtml, footerHtml }) =>
      h('html').push(
        head,
        h('body').push(
          h('').raw(headerHtml ?? ''),
          h('main').attr({ class: 'landing' }).raw(bodyHtml),
          h('').raw(footerHtml ?? ''),
        ),
      ),
  },
})
```

A page selects it in its frontmatter:

```md
---
title: Welcome
template: landing
---
```

Besides the prepared `head` and the page's `bodyHtml`, a template receives the page's shared `headerHtml` and `footerHtml`, the `site` config, `navigation`, the heading `outline`, and `pageInfo`, whose `frontmatter` includes any custom fields the page defines. A template named `doc` or `splash` replaces the built-in one. [Run code during the build](#run-code-during-the-build) shows how to style `.landing`.

## Transform Markdown

Ordinary `rehypePlugins` run before `rehypePostPlugins`, which apply final presentation before outline collection and code highlighting. The theme plugin uses this final stage for `div.table-scroll`, so tables introduced by custom transforms receive the same scrolling behavior as source tables. Both stages run on pages and shared Markdown partials.

`markdown` adds <a href="https://github.com/remarkjs/remark" target="_blank" rel="noopener">remark</a> plugins, which change the Markdown tree, and <a href="https://github.com/rehypejs/rehype" target="_blank" rel="noopener">rehype</a> plugins, which change the HTML tree. Every page, header, and footer goes through these steps:

1. PureStack reads the Markdown. Regor markup, such as `<Badge tone="success">`, stays raw HTML.
2. Your remark plugins run.
3. The Markdown tree becomes an HTML tree.
4. Your rehype plugins run.
5. PureStack collects the headings for the table of contents and highlights code.
6. Regor components render, and the template wraps the page.

Because your rehype plugins run before step 5, a heading they change also changes in the table of contents.

Install the plugins you need and list them, with options where a plugin takes them:

```ts
import { definePlugin } from 'purestack'
import rehypeExternalLinks from 'rehype-external-links'
import remarkSmartypants from 'remark-smartypants'

export const sitePlugin = definePlugin({
  name: 'site',
  markdown: {
    remarkPlugins: [remarkSmartypants],
    rehypePlugins: [[rehypeExternalLinks, { target: '_blank' }]],
  },
})
```

A plugin of your own is a function that returns a tree transform. This one makes every image load lazily:

```ts
import type { Root } from 'hast'
import { definePlugin } from 'purestack'
import { visit } from 'unist-util-visit'

function rehypeLazyImages() {
  return (tree: Root) => {
    visit(tree, 'element', (node) => {
      if (node.tagName === 'img') node.properties.loading = 'lazy'
    })
  }
}

export const sitePlugin = definePlugin({
  name: 'site',
  markdown: { rehypePlugins: [rehypeLazyImages] },
})
```

A transform also receives the file being processed. Its `path` is the page's path in the content folder, such as `blog/first.mdx`, always with forward slashes, so a plugin can treat some folders differently.

## Generate pages

`pages` adds pages that have no file of their own, such as one page per tag or one per entry of an API reference. It receives the site config and the content files, and returns the pages to add:

| Field | Value |
| --- | --- |
| `path` | The content path the page takes, such as `blog/tags/regor.mdx`. |
| `source` | The page's content, as a file at that path would hold it: frontmatter and Markdown. Give it as a string, or as a function that returns the string. |

Return an array of `{ path, source }` objects. Each object's `source` can be text or a function returning text, synchronously or asynchronously.

Example tags plugin:

```ts
import { readFile } from 'node:fs/promises'
import { definePlugin, parseFrontmatterSource } from 'purestack'

export const tagsPlugin = definePlugin({
  name: 'tags',
  async pages({ files }) {
    const postsByTag = new Map<string, string[]>()
    for (const file of files) {
      if (!file.urlPath.startsWith('/blog/')) continue
      const source = await readFile(file.absPath, 'utf8')
      const { frontmatter } = parseFrontmatterSource(source, file.relPath)
      for (const tag of (frontmatter.tags as string[] | undefined) ?? []) {
        const posts = postsByTag.get(tag) ?? []
        posts.push(`- [${frontmatter.title}](${file.urlPath})`)
        postsByTag.set(tag, posts)
      }
    }
    return [...postsByTag].map(([tag, posts]) => ({
      path: `blog/tags/${tag}.mdx`,
      source: ['---', `title: Posts tagged ${tag}`, '---', ...posts].join('\n'),
    }))
  },
})
```

An API reference can have thousands of pages, so this plugin returns functions instead. It adds one page for each JSON file in an `api/` folder beside `package.json`, and reads a file only when its page needs it:

```ts
import { readdir, readFile } from 'node:fs/promises'
import { definePlugin } from 'purestack'

export const apiPlugin = definePlugin({
  name: 'api',
  async pages() {
    const files = await readdir('api')
    return files.map((file) => ({
      path: `api/${file.replace(/\.json$/, '.mdx')}`,
      source: async () => {
        const symbol = JSON.parse(await readFile(`api/${file}`, 'utf8'))
        return ['---', `title: ${symbol.name}`, '---', symbol.summary].join('\n')
      },
    }))
  },
})
```

A generated page works like a file at its path. `blog/tags/regor.mdx` is served at `/blog/tags/regor/`, shows up in automatic navigation, uses its folder's header and footer, and other pages can [link to it](../content/links) as `./tags/regor`. Its frontmatter can select a template or set `nav` options, as in any page.

- **Paths.** A path ends in `.md`, `.mdx`, or `.rmdx` and stays inside the content folder. It cannot be a `header.mdx` or `footer.mdx`, or the path of a real file or of another plugin's page.
- **Files.** `files` lists the pages in the content folder, each with its `relPath`, its `absPath`, and the `urlPath` it is served at. Generated pages are never among them.
- **Source functions.** PureStack calls a source function to render its page and, while navigation is on, to read the page's frontmatter. Return the same text until the data behind it changes, so navigation and the page agree.
- **Updates.** `pages` runs once per build. While `serve` runs, it runs again whenever a content file or asset changes: a new tag on a post gets its page on the next reload, and a tag no one uses anymore loses its page. A page whose source is a function renders again on its next request, since PureStack keeps no text to compare.

## Run code during the build

Hooks run at fixed points in a build. Page hooks run every time a page renders, including each re-render while `serve` runs, and for generated pages too:

| Hook | Runs |
| --- | --- |
| `onPageStart(context, file)` | Before a page renders. |
| `onPageDocument(context, page)` | When its document is ready, before it becomes HTML. [Change the page's DOM](#change-a-pages-dom) here. |
| `onPageRendered(context, page)` | After it becomes HTML. Changes to `page.html` are written. |
| `onPageWritten(context, page)` | After its HTML file is written. |

The other hooks run once per full build, in this order. `serve` runs a full build when it starts and whenever `siteConfig.json` or your plugins change:

| Hook | Runs |
| --- | --- |
| `onConfigResolved(context)` | Before any output. Register styles here. |
| `onContentDiscovered(context, files)` | After the pages are found, before they render. |
| `onNavigationBuilt(context, navigation)` | After the navigation is built. |
| `onStylesWritten(context, result)` | After the theme stylesheets are written. |
| `onBuildComplete(context, result)` | After every page and asset is written. |

Every hook receives `context.config`, the resolved site config. This hook gives the `landing` template's `<main>` a background that follows the light and dark themes:

```ts
import { styleBuilder, themes } from '@purestack/ts-style'
import { definePlugin } from 'purestack'

export const sitePlugin = definePlugin({
  name: 'site',
  hooks: {
    onConfigResolved() {
      themes.forEach((theme, palette) => {
        styleBuilder.get(theme).select('.landing').css({
          background: palette.semanticTone.info.surface.rest.background,
        })
      })
    },
  },
})
```

## Change a page's DOM

`onPageDocument` receives the whole page as a document, after its components and template render: header, navigation, content, and footer. Change it with the usual DOM methods instead of editing HTML text. This hook adds the date each page's file last changed to the end of its `<main>`:

```ts
import { stat } from 'node:fs/promises'
import { definePlugin } from 'purestack'

export const lastUpdatedPlugin = definePlugin({
  name: 'last-updated',
  hooks: {
    async onPageDocument(context, { document, file }) {
      // Generated pages have no file.
      if (file.source !== undefined) return
      const { mtime } = await stat(file.absPath)
      const note = document.createElement('p')
      note.className = 'last-updated'
      note.textContent = `Last updated ${mtime.toISOString().slice(0, 10)}`
      document.querySelector('main')?.appendChild(note)
    },
  },
})
```

- **It can await.** The document stays the page's own while the hook awaits, even when `serve` renders several pages at once. Inside the hook, the global `document` is the page too, so libraries that use it work.
- **Links resolve.** Links the hook adds, such as `<a href="./themes">`, resolve and are checked like links you write in a page.
- **What it receives.** `page` holds the `document`, the page's `file`, its `frontmatter`, and the `urlPath` it is served at. For a [generated page](#generate-pages), `file.source` holds its source, and no file exists at `file.absPath`.

Use `markdown` instead to change only the page's content, and `onPageRendered` for the final HTML text.

## Write extra files

Collect page information in a page hook, then write a derived file after the full build. This example produces a JSON page index. Save it as `plugins/page-index.ts` beside the content directory:

<import-codeblock src="./plugins/page-index.ts"/>

Add the plugin in `content/purestack.config.ts`:

```ts
import { defineConfig } from 'purestack'
import { pageIndex } from '../plugins/page-index'

export default defineConfig({ plugins: [pageIndex()] })
```

After a build, open `page-index.json` in the output directory. Each entry contains a title and a public path. The plugin skips `index: false` pages and uses the same base-path helper as the framework.

- **Start clean.** `onConfigResolved` clears the collected pages for each full build.
- **Use the resolved output path.** `context.config.outDir` points to `publishDir` during a release build.
- **Know the lifecycle.** `onBuildComplete` runs after the full build. This example does not rewrite its index after every incremental page edit; run a full build to refresh it.
- **Choose the data model.** This example keys entries by public URL. A hidden-URL multilingual site needs a locale-aware key if the index must retain every translation.

## Handle requests in development

`devMiddleware` sees each request the development server receives, before the site does. Answer a request to handle it, for example to stand in for an API that your page scripts call:

```ts
import { definePlugin } from 'purestack'

export const mockApiPlugin = definePlugin({
  name: 'mock-api',
  devMiddleware(request, response) {
    if (request.url !== '/api/status') return
    response.writeHead(200, { 'content-type': 'application/json' })
    response.end(JSON.stringify({ ok: true }))
  },
})
```

- **Node's objects.** `request` and `response` are Node's [HTTP request and response](https://nodejs.org/api/http.html). `request.url` is the full path, with `basePath` if the site has one.
- **Passing a request on.** Return without sending a response, and the next plugin sees the request, then the site. A header set with `response.setHeader` still applies to whatever answers, including the site's pages.
- **Errors.** When the middleware throws, the terminal shows the error and the request gets status 500.
- **Development only.** `build` and `publish` ignore it.

## Combine plugins

List plugins in the order they should apply:

```ts
export default defineConfig({
  plugins: [sitePlugin, tagsPlugin, pageIndex()],
})
```

Hooks, remark and rehype plugins, page generators, and dev middleware all run in that order, one plugin after another. Skins, components, templates, and generated pages combine by name, so two plugins cannot add the same one; rename one of them.

For a single hook, an inline plugin is enough:

```ts
export default defineConfig({
  plugins: [sitePlugin, { name: 'notify', hooks: { onBuildComplete() {} } }],
})
```

## Share a plugin as a package

A plugin is a plain object, so a package can export one. The page-index plugin above is a factory and can be packaged with its types. The following uses `your-page-index-plugin` as a placeholder package name, not an existing PureStack dependency:

```ts
import { defineConfig } from 'purestack'
import { pageIndex } from 'your-page-index-plugin'

export default defineConfig({
  plugins: [pageIndex()],
})
```

When you publish the package:

- **Ship JavaScript.** Packages load without bundling, so publish compiled JavaScript with type declarations, not TypeScript source.
- **Share the site's PureStack.** List `purestack`, and any `@purestack/*` package the plugin imports, under `peerDependencies`, not `dependencies`. The plugin then uses the site's copy instead of installing its own.

## Cache build-time computations

Plugins and build-time components can use `PersistentCache` from
`@purestack/ts-util-node` to reuse expensive results across builds. Create one
cache per factory, use an owner namespace and implementation version, and include
all output-affecting inputs in its keys. Pass `enabled: config.cache` to honor
`--no-cache`.

Only cache computed values: dependency tracking, styles, and asset emission must
still run when a value is reused. The cache batches small values into JSON shards
and keeps bounded memory. Await `cache.flush()` after the computation batch;
periodic development flushing does not keep Node alive. Highlighters can return
an optional `flush()` method, which core awaits after each build or development
render batch, including failures. See the
[cache API and component example](https://github.com/PureStackStudio/PureStack/tree/main/packages/ts-util-node#persistent-build-cache).

## Build from a script

`buildSite` and `startDevServer` run the same build as the CLI, for a project that needs its own build script. They do not look for `purestack.config.ts`; pass plugins in `options.plugins`:

```ts
import path from 'node:path'
import { buildSite } from 'purestack'
import { sitePlugin } from './plugins/site'

await buildSite({
  siteConfig: { contentDir: path.resolve('content') },
  options: { plugins: [sitePlugin] },
})
```

To have `startDevServer` load a config file and reload it as `serve` does, pass the file's path as `configFile`. Its plugins apply after those in `options.plugins`.

## When something goes wrong

PureStack checks every plugin before the build starts, so a mistake fails at once and names the plugin:

```text
Plugin "site" has an unknown hook "onPageRender". Hooks: onConfigResolved, …
Plugins "site" and "docs" both define the component "releaseBadge".
Plugin "site" cannot replace the built-in skin "standard". Give its skin another name.
Plugin "tags" generates "blog/first.mdx", which is already a content file.
```

When a hook or page generator throws, the error names the plugin and where it failed:

```text
Plugin "page-index" failed in onBuildComplete: ENOENT: no such file or directory
```

While `serve` runs, a failing page hook shows its error on that page and leaves the server running. Most other problems are one of these:

- **`Unknown theme skin`.** The plugin with the skin is missing from `plugins`, or `purestack.config.ts` is not in the folder passed to `--content`.
- **`Could not bundle`.** An import in the config, or in a file it imports, does not resolve. The message names it.
- **`Could not run` with `document is not defined`.** A component is defined at the top of a module. Create it inside `components`, as [Add components](#add-components) shows.
- **An edit has no effect while `serve` runs.** Only the config and your own files reload. After changing a package, restart `serve`.
- **A file a hook writes is missing from the published site.** Write it into `context.config.outDir`, not a fixed folder.

## Plugin reference

Every field except `name` is optional.

| Field | Type |
| --- | --- |
| `name` | `string`, unique among the site's plugins |
| `defaults` | `boolean`; makes component and template contributions overridable defaults without changing initialization order |
| `skins` | Skins by name, each `{ create(): ThemeSkinPair }` |
| `config` | `{ resolve?: SiteConfigResolver, normalize?: SiteConfigResolver, finalize?: SiteConfigFinalizer }`; overrides, normalization, then derived settings, before factories |
| `components` | `(config) => ({ [name]: component })` |
| `templates` | Templates by name, each `(input) => TSNode<'html'>` |
| `head` | `(input) => TSNode<'head'>`, or a promise; composes head markup before the page template |
| `headConfig` | `({ site, pageInfo }) => BasicHeadConfig`, or a promise; metadata defaults before explicit page overrides |
| `styles` | `(config) => SiteStyles`; one stylesheet provider, initialized before component factories |
| `markdown` | `PureStackMarkdown`: remark, rehype, final rehype transforms, and highlighter providers |
| `pages` | `({ config, files }) => { path, source }[]`, or a promise of them; `source` is the text, or a function that returns it |
| `hooks` | Any of the hooks above |
| `devMiddleware` | `(request, response) => void`, or a promise |
